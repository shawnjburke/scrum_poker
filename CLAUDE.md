# ScrumPoker — Project Guide

This file orients Claude (or any developer) to the project's specifics. For
generic Phoenix / LiveView / Elixir rules, see [`AGENTS.md`](AGENTS.md).

## What this is

A real-time planning poker web app for agile estimation sessions. Built for
**PhoenixTeam** (an internal tool that may grow into a product). The `phx/` in
the directory path refers to the company name, not the framework — though
Phoenix is the framework we chose, which is a happy coincidence.

## Tech stack

- **Elixir 1.19** + **Phoenix 1.8** + **Phoenix LiveView 1.1** (real-time UI)
- **PostgreSQL** for persistence
- **Tailwind 4** + **daisyUI** for styling
- **phx_gen_auth** for email/magic-link authentication
- **Ueberauth** for OAuth (Google, Microsoft, GitHub configured)
- **Cabbage** (Cucumber for Elixir) for acceptance tests
- **Phoenix.Presence** for tracking who's in a room

## Quick start

Windows dev workflow uses `cmd` (not Git Bash — `iex` misrenders there).

```cmd
start_dev.bat
```

The script sets OAuth env vars and runs `mix phx.server`. It's gitignored
because it contains secrets. To set up your own, copy the secrets from
1Password (or wherever) into a fresh `start_dev.bat`.

Run tests with `mix test`. Reports appear in `test/reports/`.

## Real-time architecture (read this before changing the room LiveView)

Every participant has their own LiveView process. They coordinate via PubSub
on the topic `"room:#{room.code}"` and Phoenix.Presence on the same topic.

**Critical pattern:** event handlers should **broadcast only, never update
local assigns** for state that affects all participants. Let `handle_info`
update assigns for everyone uniformly (including the sender, who receives
their own broadcast).

Why: early bugs had the sender update assigns AND receive the broadcast,
causing duplicate messages, duplicate tickets, etc. The rule "broadcast for
shared state, assign for personal state" prevents this.

**Personal state stays local:** `my_vote`, `show_add_ticket_form`,
`mobile_tab`, etc. — these are per-user and assign directly is fine.

## Testing strategy

We have three reports generated by every `mix test` run in `test/reports/`:

1. **`features.html`** — Gherkin scenarios for stakeholders. Lead audience.
2. **`index.html`** — All 115+ tests for developers.
3. **`how_we_test.html`** — Explainer of the five testing layers.

The **Persona DSL** in `test/support/persona.ex` is the foundation. Both the
ExUnit E2E tests (`test/scrum_poker_web/e2e/`) and the Gherkin step
definitions (`test/features/`) delegate to it. If you add new test scenarios,
extend Persona first — don't drive the LiveView directly from a test.

Persona methods follow Screenplay terminology: **Tasks** are state-changing
actions (`creates_room`, `votes`), **Questions** are assertions
(`sees_consensus_at`, `sees_tickets_in_queue`).

OAuth is intentionally **not** in the test suite — it requires external
provider mocking that would obscure the flow without adding confidence.
OAuth is verified manually.

## OAuth setup

Credentials live in `start_dev.bat` (gitignored). Config in
`config/runtime.exs`. Redirect URIs registered with each provider:

- Google: `http://localhost:4000/auth/google/callback`
- Microsoft: `http://localhost:4000/auth/microsoft/callback`
- GitHub: `http://localhost:4000/auth/github/callback`

Microsoft uses tenant `common` (any Entra org + personal accounts). Some
enterprise tenants block third-party app consent by policy — that's an
org-side issue, not a code issue. See `feedback_oauth_setup.md` in personal
memory for tips on the developer consoles.

## Common pitfalls

- **`iex` in Git Bash** — broken terminal rendering. Use cmd/PowerShell.
- **`config.exs` for OAuth secrets** — evaluated at compile time, so env vars
  must already be set when you compile. Use `config/runtime.exs` instead.
- **HEEx `:if` in plain string interpolation** — `:if={...}` only works in
  HEEx templates, not regular Elixir string interpolation. Got bitten by
  this in the test reporter.
- **`rescue` in single-line `do:` functions** — syntax error. Use a
  multi-line `do…rescue…end` or restructure with `case`.
- **`consume_uploaded_entries` callback** — must return `{:ok, value}` to
  consume the entry. Returning `{:error, _}` leaves the entry uncommitted
  and gives confusing empty-list results.
- **Flash messages in custom layouts** — the room view has its own header
  (not `Layouts.app`). It still needs `<Layouts.flash_group flash={@flash} />`
  somewhere or flash messages set in event handlers go unseen.

## Conventions

- Commit messages have a one-line summary followed by a body explaining
  *why* (not just *what* — the diff shows what). End with the
  Co-Authored-By trailer.
- Don't add features or refactor beyond what a task requires.
- Tests as executable spec: each `.feature` file should read like a
  business requirement. The acceptance layer is doubly important for an
  AI-assisted project — it's the contract non-developers can audit.
